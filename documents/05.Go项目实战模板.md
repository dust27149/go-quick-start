# Go 项目实战模板

这份文档的目标不是继续讲语法，而是把前面的基础内容组织成一个可落地的 Go 小项目骨架。

重点包括：

- 项目目录怎么拆
- 包和模块怎么管理
- 配置怎么管理
- HTTP 客户端怎么封装
- 并发任务怎么组织
- 主程序怎么收尾

这份模板适合这些场景：

- 并发请求多个网址
- 调用第三方 API
- 做一个命令行网络工具
- 做一个小型服务或探测程序

版本基准：本文档以 Go 1.26.5 为基准进行介绍。

## 1. 先看目标

一个实用的 Go 小项目，至少应该具备这些能力：

1. 有清晰的入口
2. 有统一配置
3. 有明确的业务函数
4. 有错误处理
5. 有并发控制

这些边界一开始分清楚，后续代码会更稳定。

## 2. 推荐目录结构

对于一个小型 Go 项目，可以先用这样的结构：

```text
your-project-name/
  main.go
  go.mod
  app.log
  config/
    config.go
  internal/
    client/
      http_client.go
    logger/
      logger.go
    worker/
      fetcher.go
```

说明：

- `your-project-name/`：占位符目录名，可替换为你的项目目录名
- `main.go`：程序入口，只做组装和启动
- `config/`：配置读取和默认值
- `internal/logger/`：日志初始化
- `internal/client/`：HTTP 客户端封装
- `internal/worker/`：并发任务逻辑

如果项目很小，可以暂时不拆这么细，但建议先建立职责边界。

### 依赖和工具安装的约定

和前面的基础教程保持一致，这里统一用下面这套说法：

- `go get`：管理当前项目依赖（会更新 `go.mod` / `go.sum`）
- `go install`：安装命令行工具（通常带 `@版本`）

示例：

```powershell
# 安装命令行工具
go install golang.org/x/tools/gopls@latest
go install golang.org/x/tools/cmd/goimports@latest
```

在项目里，建议定期执行一次：

```powershell
go mod tidy
```

它会清理未使用依赖，并补齐缺失依赖，保持模块文件整洁。

## 3. 包和模块管理

### 定义

先建立一个最重要的认识：Go 代码通常按“文件 -> 包（package）-> 模块（module）-> 项目”来组织。

- 文件：一个 `.go` 源文件。
- 包（package）：一组同目录、同 `package` 名的 Go 文件。
- 模块（module）：一个带 `go.mod` 的项目边界，用来管理依赖。

Go Modules 是依赖管理与构建边界的基础。

它主要解决两个问题：

- 依赖版本不可控，团队成员环境不一致。
- 项目边界不清晰，构建和发布不可重复。

任何非一次性脚本的 Go 项目，都应尽早进行项目初始化生成 `go.mod`。

### 包（package）是什么

包可以理解成“代码分组单位”。把一组职责相关的函数、类型、变量放到同一个包里，便于复用和维护。

例如：

```go
package config
```

这表示当前文件属于 `config` 包。

初学阶段先记住两个规则：

- 同一个目录下的 Go 文件，通常应属于同一个包。
- 包名通常简短、直接，常和目录名保持一致，例如 `config`、`client`、`worker`。

Go 不要求像 Java 那样把 `struct`、`func`、方法等强制拆到不同文件里。只要它们属于同一个包，就可以放在同一个 `.go` 文件中。是否拆文件，主要取决于可读性和维护成本，而不是语法要求。Go 更强调“按包组织代码”，不是“按类型强制分文件”。

### 模块（module）是什么

模块可以理解成“项目边界 + 依赖边界”。

当你执行：

```powershell
go mod init your-module-name
```

Go 会在项目根目录生成 `go.mod`。从这一刻开始：

- 当前项目有了明确的模块名。
- 依赖版本会记录在模块文件中。
- 导入你自己项目里的包时，也会以模块名为起点。

例如模块名是：

```text
github.com/yourname/demo
```

那么项目里的 `config` 包可以这样导入：

```go
import "github.com/yourname/demo/config"
```

### `package main` 是什么

`package main` 表示“这个包会编译成可执行程序”。

最常见的入口文件就是：

```go
package main

func main() {
	// 程序入口
}
```

这里有两个条件：

- 包名必须是 `main`
- 必须存在 `func main()` 作为程序入口

如果缺少其中任何一个，它就不是一个可直接运行的程序包。

### `package xxx` 是什么

除了 `package main`，其他包通常都是“可复用代码包”，例如：

```go
package logger
```

这类包通常：

- 不直接作为程序入口运行
- 用来提供函数、结构体、方法、工具逻辑
- 由 `main` 包或其他包导入后使用

### `internal` 是什么

`internal` 是 Go 约定里一个很重要的目录名，用来放“只给当前项目内部使用的代码”。

你可以先把它理解成“项目内部实现细节区”。

放在 `internal/` 下的包：

- 可以被当前项目内部导入
- 不能被项目外部随意导入

这样做的好处是：

- 避免把还不稳定的实现细节暴露给外部
- 帮团队明确哪些代码是内部实现，哪些代码是对外能力

入门项目里，日志、HTTP 客户端、worker 等都适合放在 `internal/` 下。

### 常见理解

- `package` 是代码分组单位，`module` 是项目与依赖边界，它们不是同一个概念。
- `package main` 是可执行程序入口包，`package config`、`package client` 这类通常是功能包。
- 导入路径看模块名 + 目录路径，不是只看包名。
- `internal/` 不是关键字，而是 Go 识别的特殊目录约定。

## 4. 一个更真实的 main.go 应该做什么

`main.go` 不建议堆满业务细节，更适合做这几件事：

1. 加载配置
2. 初始化依赖
3. 启动任务
4. 收集结果
5. 输出结束状态

也就是说，`main.go` 更像“装配层”。

## 5. 配置管理

### 定义

入门阶段可以先用“结构体 + 默认值”，再逐步扩展。

### 最小示例

```go
package config

import "time"

type Config struct {
	LogFile string
	Timeout time.Duration
	URLs    []string
	Workers int
}

func Load() Config {
	return Config{
		LogFile: "app.log",
		Timeout: 5 * time.Second,
		URLs: []string{
			"https://example.com",
			"https://golang.org",
		},
		Workers: 3,
	}
}
```

如果你对 `struct`、函数返回值或 `time.Duration` 还不熟，建议先补基础再回到本篇。

### 工程注意点

- 简单
- 可读
- 适合初期迭代

后面再逐步扩展到：

- 环境变量
- JSON/YAML 配置文件
- 命令行参数

### 常见坑

- 配置分散在多个文件，缺少统一入口。
- 默认值与实际运行参数不一致，排查困难。

## 6. HTTP 客户端封装

### 定义

网络程序不建议到处直接写 `http.Get`，更稳妥的做法是封装客户端。

### 最小示例

```go
package client

import (
	"net/http"
	"time"
)

type Client struct {
	httpClient *http.Client
}

func New(timeout time.Duration) *Client {
	return &Client{
		httpClient: &http.Client{Timeout: timeout},
	}
}

func (c *Client) Get(url string) (*http.Response, error) {
	return c.httpClient.Get(url)
}
```

### 工程注意点

- 超时统一管理
- 后面容易加 header、重试、鉴权
- 更容易测试

### 常见坑

- 每次请求临时创建 client，难以统一配置。
- 超时、重试、鉴权散落在业务代码中。

## 7. 并发任务怎么组织

批量请求多个网址时，建议把“单个任务”和“任务调度”分开。

### 定义

任务函数负责单次请求，调度函数负责并发策略和结果汇总。

### 最小示例

单个任务：

```go
package worker

import (
	"fmt"
	"log"
	"net/http"
)

func FetchURL(httpClient *http.Client, logger *log.Logger, url string) string {
	logger.Printf("开始请求: %s", url)

	resp, err := httpClient.Get(url)
	if err != nil {
		logger.Printf("请求失败 %s: %v", url, err)
		return fmt.Sprintf("%s -> error: %v", url, err)
	}
	defer resp.Body.Close()

	logger.Printf("请求完成 %s: %d", url, resp.StatusCode)
	return fmt.Sprintf("%s -> %d", url, resp.StatusCode)
}
```

并发调度：

```go
package worker

import (
	"log"
	"net/http"
	"sync"
)

func FetchAll(httpClient *http.Client, logger *log.Logger, urls []string) []string {
	results := make([]string, len(urls))
	var wg sync.WaitGroup

	for i, url := range urls {
		wg.Add(1)

		go func(index int, target string) {
			defer wg.Done()
			results[index] = FetchURL(httpClient, logger, target)
		}(i, url)
	}

	wg.Wait()
	return results
}
```

### 工程注意点

- 每个 URL 一个 goroutine
- 用 `WaitGroup` 等待全部完成
- 用切片按原顺序收集结果

### 常见坑

- 调度层直接耦合过多业务逻辑，导致函数难测试。
- 未约束并发数量，目标服务被突发流量压垮。

## 8. channel 版并发结果汇总

如果你更想练习 channel，可以使用结果通道模式。

```go
type Result struct {
	URL        string // 请求地址
	StatusCode int // HTTP 状态码
	Err        error  // 错误信息
}
```

并发执行：

```go
func FetchAsync(httpClient *http.Client, logger *log.Logger, url string, ch chan<- Result) {
	logger.Printf("开始请求: %s", url)

	resp, err := httpClient.Get(url)
	if err != nil {
		ch <- Result{URL: url, Err: err}
		return
	}
	defer resp.Body.Close()

	ch <- Result{URL: url, StatusCode: resp.StatusCode}
}
```

收集方式：

```go
resultCh := make(chan Result)

for _, url := range urls {
	go FetchAsync(httpClient, logger, url, resultCh)
}

for range urls {
	result := <-resultCh
	if result.Err != nil {
		logger.Printf("失败: %s, err=%v", result.URL, result.Err)
		continue
	}
	logger.Printf("成功: %s, status=%d", result.URL, result.StatusCode)
}
```

这个模式的特点：

- 汇总逻辑集中
- 很适合异步任务回传结果
- 更贴近 Go 风格的通信模型

## 9. 一个最小可运行模板

### 定义

下面给一个适合入门阶段直接照着写的小程序模板。

### 最小示例

```go
package main

import (
	"fmt"
	"io"
	"log"
	"net/http"
	"os"
	"time"
)

type Result struct {
	URL        string
	StatusCode int
	Err        error
}

func newLogger(logFile string) (*log.Logger, *os.File, error) {
	file, err := os.OpenFile(logFile, os.O_CREATE|os.O_WRONLY|os.O_APPEND, 0666)
	if err != nil {
		return nil, nil, err
	}

	logger := log.New(io.MultiWriter(os.Stdout, file), "", log.Ldate|log.Ltime|log.Lshortfile)
	return logger, file, nil
}

func fetch(client *http.Client, logger *log.Logger, url string, ch chan<- Result) {
	logger.Printf("开始请求: %s", url)

	resp, err := client.Get(url)
	if err != nil {
		logger.Printf("请求失败 %s: %v", url, err)
		ch <- Result{URL: url, Err: err}
		return
	}
	defer resp.Body.Close()

	logger.Printf("请求成功 %s: %d", url, resp.StatusCode)
	ch <- Result{URL: url, StatusCode: resp.StatusCode}
}

func main() {
	logger, file, err := newLogger("app.log")
	if err != nil {
		log.Fatal(err)
	}
	defer file.Close()

	client := &http.Client{Timeout: 5 * time.Second}
	urls := []string{
		"https://example.com",
		"https://golang.org",
	}

	resultCh := make(chan Result)

	for _, url := range urls {
		go fetch(client, logger, url, resultCh)
	}

	for range urls {
		result := <-resultCh
		if result.Err != nil {
			logger.Printf("最终结果: %s 请求失败: %v", result.URL, result.Err)
			continue
		}

		logger.Printf("最终结果: %s -> %d", result.URL, result.StatusCode)
	}

	fmt.Println("全部任务完成，详情见 app.log")
}
```

### 工程注意点

- 可并发执行
- 有超时
- 有结果通道
- 有日志文件
- 有错误处理

### 常见坑

- 模板落地后不做拆分，`main.go` 再次变成“大杂烩”。
- 错误只打印不归类，后续监控和告警难接入。

## 10. 再往前一步：加配置结构

如果不想把参数硬编码在 `main` 里，可以进一步整理成配置结构：

```go
type Config struct {
	LogFile string // 日志文件名
	Timeout time.Duration // 请求超时
	URLs    []string // 待请求的地址列表
}
```

然后：

```go
cfg := Config{
	LogFile: "app.log", // 默认日志文件名
	Timeout: 5 * time.Second, // 默认超时
	URLs: []string{
		"https://example.com",
		"https://golang.org",
	},
}
```

后续切到环境变量或配置文件会更顺。

## 11. 错误处理建议

写这类程序时，建议保持两个原则：

1. 初始化失败直接退出
2. 单个任务失败不影响其他任务继续执行

比如：

- 日志文件打不开，直接退出
- 某个网址请求失败，只记录错误并继续处理其他网址

这比“一处出错全部静默失败”更可维护。

## 12. 什么时候该拆文件

如果你的 `main.go` 已经开始出现这些情况，就该拆文件了：

- 超过 150 到 200 行
- 配置、网络请求、并发逻辑全堆一起
- 一个函数既做请求又做格式化又做汇总

拆分时优先按职责拆，不要按“感觉”拆。

推荐优先级：

1. 先拆 config
2. 再拆 HTTP client
3. 再拆业务 worker
4. 最后根据需要拆更多辅助逻辑

## 13. 入门阶段不要急着做复杂的事

一开始先不要同时上这些东西：

- 太重的第三方框架
- 过度抽象接口层
- 复杂的依赖注入
- 过度泛型化设计

先把这条主线打通：

- 配置
- 请求
- 并发
- 错误处理

这已经足够支撑很多小工具和服务原型。

## 14. 一个适合你的练习路线

按下面顺序做会比较顺：

1. 先把 `main.go` 写成并发请求两个网址
2. 加上超时
3. 把请求函数拆出去
4. 增加结果结构体
5. 最后尝试做成一个可扩展的小项目目录

## 15. 总结

Go 小项目实战核心不是“代码多”，而是尽早理顺边界：

- `main` 负责装配
- 配置负责参数
- client 负责请求
- worker 负责并发任务

当这几个角色分清楚以后，哪怕项目规模变大，代码也不会很快失控。
